Zenodo record metadata for https://doi.org/10.5281/zenodo.21795712 (concept DOI,
always resolves to latest). Originally entered by hand on the v1.4.1 record at
https://zenodo.org/records/21795721.

THIS FILE IS NO LONGER A HAND-ENTRY CHECKLIST. It was one for the v1.4.1 record,
before .zenodo.json existed. Since then, .zenodo.json at the repository root has
overridden what Zenodo derives from a GitHub release, and its `description`
already carries the licensing paragraph and the copyright line as formatted HTML.
Nothing below needs pasting into the web form. Edit .zenodo.json instead.

ONE THING CANNOT COME FROM THE REPOSITORY. Zenodo's deposit schema has a singular
`license` field -- "the selected license applies to all files in this deposition"
-- so only AGPL-3.0-or-later can be set from .zenodo.json. Creative Commons
Attribution 4.0 International has to reach the record another way.

IT DOES NOT CARRY FORWARD. Zenodo's new-version flow copies much of the previous
version's metadata, but not this. The v1.5.0 record was published on 2026-08-06
with only AGPL and stayed that way until Todd added CC BY 4.0 by hand on
2026-08-07. Assume every future release starts with one licence.

SO, AFTER EVERY RELEASE, open the new record, click Edit, and fix TWO fields:

  1. Licenses -> "Add standard" -> Creative Commons Attribution 4.0 International
  2. Copyright -> Copyright (c) 2026 Michael Todd Edwards

Both are structured fields that .zenodo.json cannot populate. The copyright line
IS in the description prose, which is why the record looks complete at a glance;
the field under the Licenses block is separate and comes up empty every release.
Its placeholder reads "Copyright (C) 2026 The Authors." in grey -- that is not a
value.

Then Publish. Publishing a metadata edit on an already-published record does not
mint a new DOI.

While you are in the form, check Publication date under Basic information. Zenodo
timestamps the deposit on CERN time, so a release cut late in the UTC day lands
on the following date: v1.5.1 was tagged 2026-08-07 at 22:21 UTC and the record
said 2026-08-08. Set it to the date of the tag. Do NOT use the "Dates" section
lower down -- that is for additional dates like Accepted or Issued, each needing
a type, and it does not change the publication date.

Do make sure you are editing the record and not in a "New version" draft, which
does mint one. But DO NOT use the DOI section to tell them apart. The edit form
of a published record still shows "No, I need one" selected and still prints
"Reserve a DOI ... registered when your upload is published", which reads exactly
like a draft and is not. The reliable check is the DOI NUMBER: if it matches the
DOI of the record you meant to edit, you are editing that record. v1.5.0 is
10.5281/zenodo.21817511; the concept DOI, which the paper prints and which always
resolves to latest, is 10.5281/zenodo.21795712.

The version number comes from the GIT TAG, not from CITATION.cff. The v1.5.0
record is correctly labelled v1.5.0 even though CITATION.cff still said 1.4.4 at
the time, so a stale CITATION.cff does not mislabel the archive. It does mislabel
GitHub's "Cite this repository" button, which is the reason to keep it current.

Verified 2026-08-07 against https://developers.zenodo.org/ and the live records.

DO NOT CHECK THE LICENCES VIA THE API. https://zenodo.org/api/records/<id>
returns metadata.license as a single object, so a record carrying both licences
reports only {"id": "agpl-3.0-or-later"} -- the same answer a record carrying one
gives. It is the singular-field limitation again, showing up in the read path
this time. An API check cannot distinguish "CC BY is missing" from "CC BY is
there and unrepresentable", and reading it as the former wasted time twice on
2026-08-07. Open the record page and look at the Licenses block.
The v1.4.1 record shows the licensing under a separate Notes heading and v1.5.0
shows it inside the description; that is the difference between hand entry and
.zenodo.json, not a loss. Do not "fix" it by adding a `notes` field -- the
paragraph would then appear on the record twice.
